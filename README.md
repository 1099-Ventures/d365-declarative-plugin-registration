# D365 Declarative Plugin Registration

Register Dataverse plugin steps and images from attributes on the plugin classes themselves, and apply that registration from the command line or a pipeline, on any OS.

> **Status: early design.** The attribute shape is being settled in [`samples/Registration`](samples/Registration). The CLI does not exist yet. Names, including the namespace and package name, may still change.

## Why

Plugin steps are usually registered by hand in the Plugin Registration Tool. That tool is Windows-only, the registration it creates lives only in the target environment, and nothing ties it back to the code. Steps drift, images get forgotten, and a missing pre-image shows up at runtime as a `NullReferenceException`.

This project moves the registration next to the code:

- The plugin class declares its steps and images with attributes.
- A `dotnet` tool reads the compiled plugin assembly and reconciles Dataverse to match: assembly, plugin types, steps and images.
- `plan` shows the changes. `apply` makes them. It runs from Linux, macOS or Windows, locally or in CI.

## Declaring registrations

```csharp
[PluginStep(Message.Create, EntityLogicalNames.Lead, Stage.PreOperation)]
[PluginStep(Message.Update, EntityLogicalNames.Lead, Stage.PostOperation,
	FilteringAttributes = new[] { LeadFieldNames.FirstName, LeadFieldNames.LastName })]
[PluginImage(Message.Update, ImageType.PostImage, LeadFieldNames.FirstName, LeadFieldNames.LastName)]
public class SetLeadSubject : IPlugin
{
	...
}
```

With early-bound classes generated by `pac modelbuilder`, pass the entity as a type and use the generated field constants:

```csharp
[PluginStep(Message.Update, typeof(Lead), Stage.PostOperation,
	FilteringAttributes = new[] { Lead.Fields.FirstName, Lead.Fields.LastName })]
[PluginImage(Message.Update, ImageType.PostImage, Lead.Fields.FirstName, Lead.Fields.LastName)]
```

Rules of thumb:

- One `PluginStep` per step. Messages without a primary entity (Associate, Disassociate, global custom APIs) omit the entity.
- A `PluginImage` binds to the class's step for the same message. If the class has two steps for one message, give the step a `Key` and the image a matching `Step`.
- An image with no attributes listed includes all columns.
- `Id` pins a step to an existing registration, so steps registered by hand can be adopted without being recreated.

The tool rejects declarations that can't work, such as a pre-image on Create, a post-image on a pre-operation step, or an image with no matching step.

## How the attributes are shipped

Dataverse runs plugins in a sandbox, and every assembly a plugin references has to be deployed with it. To avoid adding a dependency, the attributes ship as a **source-only** NuGet package. The classes are `internal` and compile into your plugin assembly. The tool matches them by name and never loads your assembly, so it can inspect a .NET Framework plugin assembly from .NET on Linux.

The attribute source targets C# 7.3 so that it builds in classic .NET Framework plugin projects.

## Planned CLI

| Command | Purpose |
| --- | --- |
| `plan` | Compare the assembly's declarations with the environment and print the changes |
| `apply` | Upload the assembly and create or update plugin types, steps and images. `--prune` removes undeclared steps. `--solution` adds components to a solution |
| `export` | Read existing registrations from an environment and print them as attributes, to adopt an existing project |

Authentication will support interactive login for local use and workload identity federation for pipelines, so no client secrets are needed.

## Building the samples

```bash
cd samples/Registration
dotnet build
```

## Contributing

Contributions are welcome. The project is young, so please open an issue to discuss a change before putting significant work into a pull request.

- **Issues:** report bugs and suggest features in [GitHub Issues](https://github.com/1099-Ventures/d365-declarative-plugin-registration/issues). The maintainers plan work on an internal board and will link it back to the issue.
- **Pull requests:** branch from `main` and open a PR. `main` is protected, and every change goes through review.
- **Attribute source:** anything that compiles into plugin assemblies must stay C# 7.3 compatible and dependency-free. The samples build with `LangVersion 7.3` to check this.
- **Style:** match the surrounding code. Tabs for indentation.
